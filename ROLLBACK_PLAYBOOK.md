# Rollback Playbook — repo-assist upgrade

Goal: no agentic session should ever cost you more than a few minutes of
lost work. Set this up **before** your first Antigravity session, not
after something breaks.

---

## 1. Git discipline (your main safety net)

```bash
# Before starting ANY Antigravity task:
git status                 # must be clean — commit or stash first
git checkout -b task/<short-name>   # one branch per task, always

# After Antigravity finishes a task:
git diff                   # read every changed line before accepting
git add -p                 # stage selectively if the agent touched
                            # more than you asked for
git commit -m "..."        # small, reviewable commits — not one giant
                            # commit per session

# If a session goes sideways mid-task:
git checkout .              # discard uncommitted changes, instantly
git reset --hard HEAD       # nuke everything since last commit
git checkout main && git branch -D task/<short-name>   # abandon the branch entirely
```

**Rules:**
- **Never let Antigravity work directly on `main`.** One task = one
  branch. If the task was bad, delete the branch — `main` is untouched.
- **Never accept a multi-file diff you haven't actually read.** If it's
  too large to read in one sitting, that's a signal the task was scoped
  too broadly — split it (see §4).
- **Commit *before* running anything that could be destructive** (a
  rebuild script, a migration, `build_full_graph.py`), so "undo" is
  always one `git reset --hard` away.
- Tag known-good states explicitly, not just via branch history:
  ```bash
  git tag checkpoint-cli-milestone   # after step 4 in ARCHITECTURE.md §7
  git tag checkpoint-pre-fastapi     # before wrapping in FastAPI
  ```
  Tags are cheap and let you say "go back to exactly this" without
  hunting through commit messages later.

## 2. Database rollback (SQLite is not covered by git in a useful way)

The graph DB (`data/code_graph.db`) is large, binary, and regenerated by
running the phase scripts — treat it as a **build artifact**, not source.

```bash
# Before any schema change or generalization run:
cp data/code_graph.db data/code_graph.db.bak-$(date +%Y%m%d-%H%M)

# If a run corrupts or wrongly mutates the DB:
cp data/code_graph.db.bak-<timestamp> data/code_graph.db
```

- Add `data/*.db.bak-*` to `.gitignore` — you don't want these in the
  repo, just on disk as local safety nets.
- Because Phase 1–3 are (mostly) deterministic pipelines run against
  pinned repo snapshots, **the DB is always reconstructable from
  scratch** by re-running `build_full_graph.py` → Phase 2 → Phase 3. If
  in doubt and a backup isn't handy, rebuilding is a valid "rollback" —
  just slower. This is a real advantage of this project's design: worst
  case is time lost, not data lost.
- Once you're multi-repo (the FastAPI stage), back up before any schema
  migration specifically, since a migration touching the shared
  `repo_id`-scoped tables is the one change type that can silently
  corrupt data for *every* ingested repo at once, not just the one
  you're working on.

## 3. Antigravity-specific session hygiene

- **One task per session, narrow scope.** Re-read ARCHITECTURE.md §5
  (the "explicitly told" block) at the start of every session that
  touches Phase 1–3, schema, or the query layer — paste it in fresh,
  don't rely on the agent remembering context from an earlier session.
- **Ask for a plan before code.** Have Antigravity state which files it
  intends to touch before it starts editing. If the list includes
  `graph_schema.py` or table definitions and you didn't expect that,
  stop and ask why before it proceeds.
- **Run the regression check after every Phase 1–3 change**, not just at
  the end of the day:
  ```bash
  # however your grader/CLI currently invokes it —
  repo-assist ask httpx "<a known-good question>"
  repo-assist ask got "<a known-good question>"
  ```
  If either regresses, you know *immediately* which commit caused it,
  and reverting one commit is trivial. Finding out three tasks later
  means untangling three tasks' worth of changes.
- **If Antigravity proposes touching more files than the task implies,
  that's the signal to stop**, not a reason to trust it more because it
  "found more to fix." Scope creep in an agentic edit is exactly how
  Phase 1/2/3 contracts get silently broken.

## 4. If a task is too big to safely review as one diff

Split it. Concretely, for this project, that means tasks like:

- ❌ "Generalize the pipeline to work on any repo" (too broad — this is
  the exact phrasing the earlier review flagged as dangerous)
- ✅ "Add per-file language dispatch in `extract_symbols.py` so `.ts`
  files route to the TS grammar, without changing the output schema"
- ✅ "Add bounded history fetching (max 300 PRs) to `mine_history.py`,
  with a config constant, no other behavior changes"
- ✅ "Add `repo_id` column to the `symbols` and `edges` tables, migrate
  existing httpx/got data to a fixed `repo_id`, update `query_tools.py`
  reads to filter by it"

Each of these is reviewable as a diff in a few minutes and revertible
independently if wrong.

---

## 5. Quick reference — "something broke, what do I do"

| Symptom | Fix |
|---|---|
| Uncommitted changes look wrong mid-session | `git checkout .` |
| Committed changes on current branch are wrong | `git reset --hard HEAD~1` (or further back) |
| Whole task/branch was a bad idea | `git checkout main && git branch -D task/<name>` |
| DB looks corrupted or wrongly mutated | restore from `.bak-<timestamp>`, or rebuild via Phase 1–3 scripts |
| httpx/got regression after a change | `git log` to find the commit, `git revert <sha>` (keeps history, safer than reset once you've pushed/shared) |
| Not sure what changed in a big session | `git diff main...task/<name>` to see the full delta before deciding whether to merge |
